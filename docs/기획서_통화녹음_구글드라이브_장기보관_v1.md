# 기획서: 통화 녹음 구글 드라이브 장기 보관 v1

작성 2026-11-01 · 상태: **확정** (2026-11-01 대표님 답변 반영, 14장) · 다음: 1단계(스테이징)

## 1. 왜 바꾸나

- 통화 녹음은 나중에 증거로 쓸 수 있다. 사건이 끝날 때까지, 대략 **1년 이상** 보관해야 한다.
- 지금 앱 자동 업로드(1.5.0)는 Supabase 저장소에 **7일**만 보관한다. 무료 플랜 저장 공간이 1GB라서 오래 둘 수 없다.
- 고객사(회사)마다 **자기 회사 구글 드라이브**에 녹음을 쌓는다. 이렇게 하면 녹음의 주인이 그 회사가 된다. 리드마스터와 계약이 끝나도 녹음은 회사 드라이브에 남는다.

## 2. 지금 상태 (2026-11-01 운영 DB 확인)

| 경로 | 저장 위치 | 보관 | 공개 범위 | 현재 양 |
|---|---|---|---|---|
| 앱 자동 업로드 (1.5.0~) | Supabase `call-recordings` 비공개 버킷 | 7일 뒤 자동 삭제 | 회사 안 권한자만 | **0건** (아직 올라간 녹음 없음) |
| 웹 수동 업로드 | Apps Script → 본사 구글 드라이브 | 지우기 전까지 | **링크 있으면 누구나** (`ANYONE_WITH_LINK`) | 리드 **406건**에 녹음 링크 있음 |

- 지금 Supabase에 쌓인 녹음이 없으므로, 7일 자동 삭제로 사라질 녹음도 없다.
- 수동 업로드 파일은 공개 링크다. 링크가 밖으로 나가면 누구나 들을 수 있으니, 증거·개인정보 보관 방식으로는 위험하다.

## 3. 목표

1. 녹음 원본은 **각 회사 구글 드라이브**에 저장하고, 보관 기간은 회사가 정한다(기본 무기한).
2. 파일은 **비공개**로 둔다. 리드마스터 안에서 그 리드를 볼 권한이 있는 사람만 듣는다.
3. 앱 자동 업로드와 웹 수동 업로드를 **같은 저장 방식**으로 합친다.
4. 증거로 쓸 수 있게 **원본 그대로** 보관한다(다시 압축하지 않음). 올릴 때 파일 지문(SHA-256)을 기록해 "바뀌지 않은 원본"임을 보여줄 수 있게 한다.
5. AI 정리(요약·대화록·채무 정리)는 지금처럼 동작한다.

## 4. 방식 비교

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 회사별 구글 드라이브 연결 (권장)** | 회사 관리자가 설정에서 "구글 드라이브 연결"을 누르고 자기 회사 구글 계정으로 허락한다. 서버가 그 드라이브에 올린다. | 녹음 주인 = 회사. 저장 비용도 회사가 부담. 회사별로 완전히 나뉨. | 구글 OAuth 화면 설정이 필요하다(아래 9장). |
| B. 지금 Apps Script 그대로 | 모든 회사 녹음이 본사 드라이브 한 곳에 쌓인다. | 바로 쓸 수 있다. | 다른 회사 녹음이 본사 드라이브에 섞인다. 판매용으로 쓸 수 없다. 공개 링크 문제도 남는다. |
| C. 서비스 계정 + 공유 드라이브 | 리드마스터 서버 계정이 회사의 공유 드라이브에 올린다. | 토큰 관리가 단순하다. | 공유 드라이브는 Google Workspace(유료)에만 있다. 개인 구글 계정 회사는 쓸 수 없다. |

**권장: A.** 권한은 `drive.file`만 요청한다. 리드마스터가 만든 파일과 폴더만 다룰 수 있고, 회사 드라이브의 다른 파일은 보지도 못한다. 구글은 이 권한을 "민감하지 않은 권한"으로 분류해 권장한다([Choose Google Drive API scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)).

## 5. 동작 흐름 (방식 A)

### 5.1 회사 드라이브 연결 (관리자 1회)
1. 팀 관리 → 녹음 설정 → **[구글 드라이브 연결]**
2. 구글 로그인 창에서 회사 대표 계정을 고른다. 녹음을 쌓을 계정이라 직원 개인 계정은 피하는 것이 좋다.
3. 서버가 갱신 토큰(refresh token)을 **암호화해서 보관**한다. 브라우저와 폰에는 내려보내지 않는다.
4. 드라이브에 폴더 `리드마스터 통화녹음`을 만들고 시험 파일을 올렸다 지운다. 성공하면 "연결됨 (abc@회사.com)"으로 표시한다.

### 5.2 앱 자동 업로드 (매 통화)
지금 1.5.0의 녹음 찾기 부분(통화가 끝나고 20초 뒤 + 15분마다, 리드 번호만, 40초 이상)은 그대로 둔다. 바뀌는 것은 "어디에 올리나"뿐이다.

1. 앱 → 서버 `recording-upload-start`: "이 리드, 이 통화, 파일 크기·지문 이렇게 올리겠다"
2. 서버: 권한 확인(이 상담원이 이 리드를 볼 수 있나) → 회사 드라이브에 **이어 올리기(resumable) 업로드 주소**를 만들어 앱에 준다. 구글 토큰은 앱에 주지 않는다.
3. 앱 → 구글 드라이브에 파일을 직접 올린다. 끊기면 이어서 올린다. 와이파이에서만 올리기 설정도 그대로 쓴다.
4. 앱 → 서버 `recording-upload-finish`: 서버가 드라이브에서 파일 크기·체크섬을 확인하고 DB에 "보관 완료"로 기록한다.
5. AI 정리가 켜져 있으면 서버가 드라이브에서 파일을 받아 Gemini로 정리한다(지금 recording-analyze와 같은 방식).

녹음 파일이 Supabase를 거치지 않으므로 Supabase 저장 공간과 대역폭을 거의 쓰지 않는다.

### 5.3 웹 수동 업로드
리드 상세에서 파일을 고르면 같은 방식(업로드 주소 받기 → 드라이브에 직접 올리기 → 확인)으로 올린다. Apps Script 녹음 업로드는 쓰지 않는다.

### 5.4 듣기
- 리드 상세 "통화 녹음·AI" 탭에서 재생한다. 서버(`recording-play`)가 권한을 확인한 뒤 드라이브에서 받아 흘려보낸다. 파일은 계속 비공개로 남는다.
- 관리자에게는 **[드라이브에서 열기]** 버튼을 보여준다. 회사 계정으로 구글 드라이브를 직접 연다.
- 대가: 재생할 때마다 파일 크기만큼 Supabase 대역폭을 쓴다(3분 통화 ≈ 3MB). 듣기는 업로드보다 훨씬 드물어서 감당할 수 있는 양이다. 접근 기록(015)에 "녹음 재생"으로 남긴다.

### 5.5 폴더 구조 (증거로 찾기 쉽게 리드별)
```
리드마스터 통화녹음/
  2026/
    김김김_4901_<리드ID 앞 8자리>/
      20261101_183512_발신_상담원홍길동_3분12초.m4a
      20261102_101030_수신_상담원홍길동_1분05초.m4a
```
- 파일 설명 칸에 리드 ID, 고객 번호, 상담원 이메일, 통화 시각, 길이, SHA-256을 적는다. 드라이브 검색으로도 찾을 수 있다.
- 연도 폴더는 리드 등록 연도 기준이다. 같은 리드의 녹음은 한 폴더에 모인다.

## 6. 보관·삭제

- **자동 삭제 없음.** 증거 보관이 목적이라 리드마스터가 스스로 지우지 않는다. 정리는 각 회사가 한다.
- **관리자 메뉴 "오래된 녹음 정리"** (팀 관리 → 녹음 설정, 회사 관리자만):
  1. 기준을 고른다: "통화한 지 N개월 지난 녹음" (3·6·12·18·24개월 또는 직접 입력). 선택 조건으로 "리드 상태가 ○○인 것만"(예: 진행불가·고객취소·종결)을 붙일 수 있다.
  2. **미리 보기**: 지울 녹음 수, 용량, 가장 오래된·최근 통화일, 리드 목록(고객명·번호 뒤 4자리·상태·녹음 수)을 보여준다. 리드 단위로 체크를 빼서 남길 수 있다.
  3. 확인 창에 지울 개수를 직접 입력해야 실행된다(실수 방지).
  4. 실행: 드라이브 파일을 **드라이브 휴지통으로 옮긴다**(구글이 30일 뒤 완전히 지움, 그 전에는 드라이브에서 되살릴 수 있음). DB에는 "파일 삭제됨 · 삭제한 사람 · 시각"을 남긴다. AI 요약·채무 정리·메모는 남긴다. 체크하면 AI 대화록도 같이 지운다.
  5. 접근 기록(015)에 "녹음 정리 N건"으로 남긴다.
  - 한 번에 최대 500건씩 처리하고 진행률을 보여준다. 중간에 끊겨도 다시 누르면 남은 것부터 이어서 한다.
- 리드를 휴지통에 넣거나 영구 삭제해도 녹음 파일은 지우지 않는다(증거 보존). 영구 삭제 때 "녹음 N개는 드라이브에 남아 있습니다"라고 알려준다.
- 개인정보 참고(판단은 대표님): 통화 녹음은 고객 개인정보다. 개인정보 처리방침에 보관 목적(분쟁 대비 증거)과 기간(예: 사건 종료 후 1년)을 적어 두면 근거가 된다. 대화 당사자가 하는 녹음 자체는 통신비밀보호법 위반이 아니라고 알려져 있다.

## 7. 저장 용량·비용 (회사가 부담)

대표 폰 실측: T전화 녹음 ≈ **1MB/분**.

| 가정 | 값 |
|---|---|
| 상담원 1명이 하루에 올리는 녹음 (40초 이상) | 30건 |
| 평균 길이 | 3분 → 3MB |
| 하루 | 90MB / 명 |
| 한 달(22일) | 약 2GB / 명 |
| 1년 | 약 24GB / 명 |
| **상담원 30명 회사, 1년** | **약 720GB** |

- 구글 무료 15GB로는 상담원 1명 기준 약 7개월이다. 고객사는 **Google One 2TB 또는 Google Workspace**가 필요하다(요금은 계약 시점에 구글 공식 가격 확인).
- 리드마스터 쪽 비용: 녹음이 Supabase에 쌓이지 않으므로 저장 비용이 거의 없다. 재생할 때만 대역폭을 쓴다.
- 드라이브가 꽉 차면 업로드가 실패한다. 이때 앱은 폰에 파일을 그대로 두고 다시 시도하고, 관리자 화면에 "드라이브 용량 부족"을 빨간색으로 띄운다.

## 8. 실패 처리 (녹음을 잃지 않기)

- 원본은 폰에 남아 있다. 앱은 드라이브 "보관 완료"를 확인하기 전까지는 "올림" 처리를 하지 않고 다음에 다시 시도한다.
- 드라이브 연결이 끊긴 경우(관리자가 구글에서 권한 해제, 비밀번호 변경 등): 업로드를 멈추고, 회사 관리자에게 "드라이브 다시 연결 필요"를 알린다. 상담원에게는 녹음이 폰에 남아 있고 다시 연결되면 자동으로 올라간다고 보여준다.
- 팀 관리 화면에 상담원별 "올라가지 않은 녹음 N건 · 마지막 업로드 시각"을 보여준다. 폰이 꺼져 있거나 로그아웃된 상담원을 찾을 수 있다(오늘 문자 미발송과 같은 종류의 문제를 조용히 넘기지 않기 위해).
- 폰 녹음 폴더를 정리하는 앱이 있으면 원본이 사라질 수 있다. 시범 운영 때 상담원 폰 설정을 안내한다.

## 9. 보안

- 회사 드라이브 갱신 토큰은 DB에 암호화해서 저장한다(Supabase Vault). 클라이언트는 읽지 못하게 한다. 텔레그램 봇 토큰(008)과 같은 원칙이다.
- 권한은 `drive.file` 하나만 받는다. 리드마스터가 만든 녹음 폴더 밖은 볼 수 없다.
- 업로드 주소는 그 파일 하나에만 쓰이고 짧게 만료된다. 앱은 구글 토큰을 가지지 않는다.
- 파일 공유는 기본 비공개다. `ANYONE_WITH_LINK`는 쓰지 않는다.
- 구글 OAuth 설정: 지금 로그인에 쓰는 OAuth 클라이언트(프로젝트 703402707746)에 Drive API를 켜고 동의 화면에 `drive.file`을 추가한다. 민감하지 않은 권한이라 구글의 보안 심사는 필요 없을 것으로 보이지만, 외부 회사가 쓰려면 동의 화면을 "프로덕션"으로 게시하고 브랜드 확인을 받아야 할 수 있다. 시범 단계에서 확인한다.

## 10. 바뀌는 것 (구현 범위)

**DB (새 마이그레이션 017, 스테이징 먼저)**
- `org_drive_connections`: org_id, google_email, 암호화된 refresh_token, 루트 폴더 id, 연결한 사람, 상태(connected/revoked/quota_full), 마지막 오류
- `call_recordings`에 칸 추가: storage_kind('supabase'|'gdrive'), drive_file_id, drive_folder_id, sha256, size_bytes, archive_status(pending/uploading/archived/failed), archived_at, source('app'|'web')
- `org_recording_settings`: 삭제 후보 규칙(끈 상태가 기본), 보관 방식
- 리드별 드라이브 폴더 id를 기억하는 표(같은 리드 폴더를 다시 만들지 않게)

**서버 (Edge Function)**
- `drive-connect`: 연결 시작·콜백·해제·상태·시험 업로드 (관리자만)
- `recording-upload-start`, `recording-upload-finish`: 업로드 주소 발급·완료 확인 (상담원·관리자, 리드 권한 확인)
- `recording-play`: 권한 확인 후 재생(구간 재생 지원)
- `recording-analyze`: 드라이브에서 파일을 받도록 수정

**앱 1.6.0**
- `RecordingSyncWorker`: Supabase 업로드 대신 업로드 주소 받기 → 드라이브에 이어 올리기 → 완료 알림. 파일 지문(SHA-256) 계산
- 실패 시 폰에 원본 유지 + 다시 시도

**웹**
- 팀 관리 → 녹음 설정: 드라이브 연결, 연결 상태, 용량 경고, 상담원별 미업로드 현황
- 리드 상세 녹음 업로드: 드라이브 방식으로 교체
- 녹음 탭: 재생·드라이브에서 열기·지문 표시
