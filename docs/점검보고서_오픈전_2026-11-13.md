- 참고: `scripts/verify_multitenant_isolation.mjs`는 로컬 가상 DB에 마이그레이션을 골라 올리는데, 실패한 파일은 경고만 내고 넘어가며 019·021·022·024·027(공지)·028(업체)·030~033은 아예 넣지 않는다. 그래서 "14개 통과"가 새 테이블들의 격리는 보장하지 않는다.

### B2. 정산 손익(P&L)·상담원 수당 계산 오류 (`services/settlementMasterService.ts`)
코드 리뷰로 확인(운영 데이터로 재현은 안 함):
- 지출은 **만원 단위**(`types.ts:435`)인데 손익에서 원으로 더함 → 지출 300만원이 ₩300으로 반영 (`:432`).
- 매출에 부가세 포함 청구액을 씀 → 부가세 별도 거래처면 매출·순이익 10% 부풀림 (`:402`).
- 회사 고정 마진·상담원 고정 수당을 **건별이 아니라 상담원 합계에 한 번만** 적용 (`:348`). 예: 120만원 3건, 회사 고정 마진 30만 → 상담원에게 60만원 과다 지급으로 표시.
- 상담원 수당 기준 수수료가 거래처 수당 규칙(commissionRules)을 무시하고 기본 20% (`:311`).
- 손익에서 달을 골라도 매출·상담원 수당은 전체 기간 합 (DB 원가·지출만 기간 필터).
- 리뷰어 예시: 실제 −₩2,360,000인 달이 화면에는 순이익 ₩799,700(45%)로 나옴.
- 3단계 주간 정산 묶음 합계가 그 주 신규 금액이 아니라 누적 금액 → **같은 수수료가 여러 주에 다시 청구**될 수 있음 (`services/api.ts:2239, 2309`). 건별 표시(`thisWeekPayable`)와 묶음 합계가 서로 다름.
- 지출(`expenses`)은 서버에 쓰기만 하고 다시 읽지 않음 → 다른 기기에서 지출 1건 추가하면 서버의 지출 목록 전체가 그 1건으로 덮임 (`api.ts:2370`).

**조치**: 손익·수당·주간 묶음 계산을 `utils/settlement.ts`(점검 16항목 통과) 기준으로 맞추고, `scripts/settlement_check.ts`에 분배 모델·손익 시험 항목 추가. 고칠 때까지 손익·수당 탭에 "검증 중" 표시 권장.

### B3. 다른 회사 데이터가 본사 구글 시트로 전송
`syncToSheet`가 회사 구분 없이 본사 Apps Script(`VITE_GOOGLE_SCRIPT_URL`)로 리드 일괄 등록분·거래처·상태·허용 이메일·지출·정산 배치를 보낸다 (`services/api.ts:214-261, 1129-1458, 1916-1920, 2074, 2371`). 운영 배포에 URL·토큰이 들어가고(`deploy.yml:39-40`), 번들에서도 확인됨. 고객사가 쓰면 그 회사 리드가 본사 시트로 가고, 본사 `settings.expenses`가 덮일 수 있다. 토큰이 번들에 있으므로 누구나 본사 시트에 쓸 수도 있다.
**조치**: 본사(org 00000000-…-0001)가 아니면 시트 전송을 끄고, 장기적으로 시트 연동 자체를 서버 함수로 옮기거나 제거.

### B4. 앱 정식 서명 키 비밀번호가 공개 저장소에 있음
`scripts/app_build_release.mjs:11`에 정식 키(`leadmaster-release.jks`) 비밀번호가 그대로 있고, 커밋 `571feeb`로 **공개(PUBLIC) 저장소** `9981mark-hub/leadmaster-crm`에 올라가 있다(값은 이 보고서에 적지 않음). `.jks` 파일은 git에 없어서 파일이 새지 않는 한 바로 악용되지는 않지만, git 기록에 영구히 남는다.
- 게시 APK(`public/app/LeadMaster.apk`, 1.8.1)는 이미 이 정식 키(7ee0d49a…)로 서명돼 있다. 예전 디버그 키(66b2246b…)로 깔린 폰은 앱 안 업데이트가 실패한다(대표 폰·보조 폰 서명 상태는 이번에 확인 못 함).
**조치(대표님 결정)**: 스크립트가 비밀번호를 `keystore.properties`/환경변수에서 읽게 고치고 파일에서 삭제. 키를 바꿀지 결정 — **고객사 폰에 설치하기 전인 지금이 바꾸는 비용이 가장 적은 시점**(바꾸면 기존 폰은 지우고 다시 설치). 저장소 비공개 전환도 같이 검토.

### B5. 구글 API 키가 소스·번들에 하드코딩
`services/speechService.ts:17`에 Google API 키(AIza…)가 코드에 직접 들어 있고, 운영 번들(TrainingCenterPage)에도 포함된다. 어떤 API·웹사이트 제한이 걸린 키인지 확인 못 함. 제한이 없으면 누구나 이 키로 유료 TTS 등을 호출해 요금이 나온다.
**조치**: 키 제한 확인 → 서버 함수(edge-tts 등) 경유로 바꾸고 키 교체.
(참고: `VITE_GOOGLE_PICKER_API_KEY`는 Picker 전용·웹사이트 제한 키로 브라우저 노출이 정상 설계.)

### B6. 앱 WebView 허용 주소 검사가 너무 넓음 (`AppConfig.kt:18-21`, `MainActivity.kt`)
`isOurHost`가 `contains("vercel.app")`, `contains("github.io")`, `contains("lmaster.xyz")`로 검사해서 아무 `*.vercel.app`, `*.github.io`, `lmaster.xyz.evil.com` 페이지도 앱 WebView 안에서 열리고, 그 페이지가 `AndroidBridge`를 쓸 수 있다(바로 발신 `makeCall`, `setAppSession`으로 남의 세션 심기 → 그 폰 통화·문자 기록이 공격자 회사로 업로드, 캡처 차단 해제 등). URL 어디든 `google.com`이 들어 있으면 WebView 안에 두는 검사도 있다.
**조치**: 정확한 호스트 목록(`www.lmaster.xyz`, `lmaster.xyz`, `leadmastercrm.vercel.app`, `9981mark-hub.github.io`)과 `Uri.host` 완전 일치 비교, 브리지 메서드에서 현재 페이지 출처 확인.

### B7. 통화 메모가 다른 고객 리드에 저장될 수 있음 (`QuickMemoActivity.kt`)
singleTop + CLEAR_TOP으로 띄우는데 `onNewIntent`가 없다. 메모 카드가 열린 채 다음 고객 전화가 오면 새 고객 정보가 무시되고, 저장하면 **이전 고객 리드에 들어간다**.
**조치**: `onNewIntent`에서 고객 정보 갱신(작성 중 글은 이전 고객 키로 임시 저장), 저장 직전 caseId·번호 일치 확인.

### B8. 실제 상담원 계정으로 끝까지 확인한 적 없음
운영에 상담원(agent) 계정이 하나도 없다. 상담원 화면 차단은 코드로는 맞지만(🟢 참고), 배정 리드만 보이는지·팀 관리 변경(B1 때문에 지금 실패)·앱 로그인까지 실제 계정으로 확인되지 않았다.
**조치**: B1 해결 후 시범 계정(예: 2882a@naver.com을 상담원으로) 하나로 웹·앱 전 과정 확인.

### B9. 수신 팝업 업데이트 경로 재확인 필요
11-06 보조 폰 시험에서 삼성이 "출처 모르는 앱"의 통화 중 화면 위 표시를 막는 것을 확인했고, AGY가 1.7.x에서 일반 화면(Activity)+알림으로 대체했다. 이후 1.8.1까지 바뀌었지만 **앱 메뉴 업데이트로 받은 폰에서 팝업·메모가 되는지는 다시 확인 기록이 없다**(점검 목록 3단계 미완). 정식 키 전환(B4)과 겹쳐 고객사 폰 설치 절차가 정해지지 않았다.
**조치**: 보조 폰에 정식 키 1.8.1 새 설치 → 앱 메뉴로 다음 버전 받기 → 수신 카드·메모 저장 확인(`docs/점검목록_시범운영_전_앱_v1.md`).
