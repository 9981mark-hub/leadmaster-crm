## 2. 🔍 6대 보안 핵심 영역별 상세 점검 결과

### ① 멀티테넌트 완전 격리 및 행 수준 보안 (RLS)
- **점검 내용**: 타 법률사무소(회사 B)의 상담원이나 해커가 URL/API를 조작하여 회사 A의 채무자 정보를 조회·변조할 수 있는지 검증.
- **방어 메커니즘**:
  - PostgreSQL 엔진 수준에서 `current_org_id()` 및 `can_access_case()` 함수를 강제하는 RLS(Row Level Security) 정책 100% 적용.
  - 상담원은 **자신에게 배정된 리드(`assigned_user_id = auth.uid()`)만 열람 가능**하며, 타 상담원이나 미배정 리드는 목록에 노출되지 않음.
  - 비로그인(anon) 사용자의 접근 시도는 모든 테이블에서 `0건 반환 (Zero-Access)`.
- **실증 검증**: `scripts/verify_multitenant_isolation.mjs` 자동화 격리 테스트 수행 결과 **11개 공격 시나리오 전수 차단 (0 errors, 0 leaks)**.

### ② 시크릿(Secrets) 및 마스터 키 유출 방지
- **점검 내용**: 프론트엔드 JS 번들(HTML/JS)이나 안드로이드 APK를 디컴파일했을 때 DB 마스터 키나 API 비밀값이 탈취될 수 있는지 점검.
- **방어 메커니즘**:
  - `SUPABASE_SERVICE_ROLE_KEY`는 서버 환경(Deno Edge Function)에서만 실행되며, 웹 브라우저나 앱 클라이언트로 일체 번들링되지 않음.
  - 프론트엔드에는 RLS 정책에 의해 철저히 제어되는 공개 익명 키(`VITE_SUPABASE_ANON_KEY`)만 포함됨.
  - Google Drive OAuth 토큰은 PostgreSQL Vault에 암호화 보관되며, 폰이나 브라우저에 토큰 원문이 노출되지 않고 One-Time Resumable Upload URL만 교환함.

### ③ 통화 녹음 및 채무 상담 음성 데이터 보호
- **점검 내용**: 전화 통화 녹음 파일에는 주민등록번호, 계좌번호, 채권자 명단 등 치명적인 음성 정보가 포함되므로 안전한 저장 및 스트리밍 체계 점검.
- **방어 메커니즘**:
  - **Zero-Central Storage**: 리드마스터 중앙 서버에는 녹음 원본을 보관하지 않고, 각 고객사의 비공개 Google Drive에 직접 암호화 보관.
  - **HMAC-SHA256 시한부 스트리밍**: CRM에서 녹음 청취 시 서버가 1시간 유효한 암호화 서명 URL 발급(`recording-play`). 권한이 없는 타사 상담원의 URL 조작 시 즉시 403 차단.
  - Google Drive 파일 자체는 '웹에 공개'되지 않으며, 서버의 인증 프록시를 통해서만 보안 스트리밍 재생.

### ④ 클라이언트 취약점 (XSS, Eval, CSV/Formula Injection)
- **점검 내용**: 악성 스크립트 실행(XSS) 및 엑셀 다운로드를 통한 악성코드 실행(CWE-1236) 점검.
- **진단 및 조치**:
  - **XSS 방어**: 전체 코드베이스 내 위험 함수(`dangerouslySetInnerHTML`, `eval()`, `new Function()`) 0건 확인. React 가상 DOM 엔진의 기본 문자열 이스케이프에 의해 방어됨.
  - **Formula Injection 방어 완료**: 고객명이나 사전정보에 `=cmd|...`, `@`, `+`, `-` 등의 수식 구문이 삽입된 리드가 존재하더라도, 엑셀 내보내기 시(`utils/xlsxExport.ts`) 자동으로 단일 따옴표(`'`)를 앞에 붙여 단순 텍스트로 무력화(Sanitization)하는 보안 패치 적용.
  - **내보내기 권한 통제**: 엑셀 다운로드는 일반 상담원에게는 화면 버튼이 숨겨지며, 서버 및 스크립트 단에서 `canExportCaseData()`를 통해 **회사 관리자(Admin/Owner)만 실행 가능**하도록 통제.

### ⑤ 법정 개인정보 접근 기록 (Audit Trail) 및 위변조 방지
- **점검 내용**: 개인정보보호법 제29조 및 개인정보 안전성 확보조치 기준 제8조에 따른 접속기록 보관 준수 여부.
- **방어 메커니즘**:
  - `access_logs` 테이블을 통해 **리드 열람(`case_view`), 엑셀 내보내기(`export`), 녹음 청취(`recording_play`), 삭제(`case_purge`)** 시 행위자 이메일, 시각, 건수를 자동 기록.
  - **위변조 원천 방지**: DB `BEFORE INSERT` 트리거(`access_logs_stamp`)가 작동하여 기록 시각(`now()`)과 사용자 이메일을 서버 토큰에서 강제로 각인. 클라이언트가 로그를 날조할 수 없음.
  - 감사 로그 테이블에는 UPDATE/DELETE RLS 정책이 존재하지 않아 **누구도 기록을 수정하거나 삭제할 수 없는 영구 불변(Append-Only)** 구조.
  - 마스킹 처리: 삭제된 리드의 로그에도 이름과 전화번호 뒷자리만 마스킹(`김*수 ·1234`) 보관하여 감사 로그 자체의 개인정보 2차 누수 방지.

### ⑥ 모바일 앱 (LeadMasterApp) 샌드박싱 및 통신 보안
- **점검 내용**: 상담원 스마트폰에 설치되는 안드로이드 앱의 보안 설정 점검.
- **방어 메커니즘**:
  - `usesCleartextTraffic="false"`: 안전하지 않은 평문 HTTP 통신을 운영체제 차원에서 완전 차단 (HTTPS 통신만 허용).
  - `allowBackup="false"`: 스마트폰 클라우드 백업이나 ADB 백업을 통해 로컬 설정이나 채무자 캐시가 외부로 추출되는 경로 차단.
  - 내부 컴포넌트 비공개: `CallerOverlayService`, `PhoneMonitorService` 등 핵심 백그라운드 서비스에 `android:exported="false"`를 적용하여 외부 악성 앱의 서비스 호출 방어.
  - 정식 프로덕션 Keystore(`leadmaster-release.jks`, SHA-256: `7ee0...`) 서명 빌드 적용.

## 3. 🛡️ 긴급 대응 및 파기 프로세스 (Right to be Forgotten)

1. **회사 데이터 긴급 영구 파기(Kill-Switch)**:
   - 계약 해지 또는 비상 상황 발생 시 회사 대표(Owner)는 `emergency_purge_company_data()`를 통해 해당 회사의 모든 리드, 녹음 메타데이터, DNC 목록을 원자적(Atomic Transaction)으로 완전 소각 가능.
   - 파기 완료 시 법적 소명용 증빙(`org_purge_audit_logs`)이 생성되어 추후 법적 분쟁 대비.
2. **보관 주기 및 파기 자동화**:
   - `024_lead_lifecycle_archiving.sql` 및 `025_retention_policy_options.sql`을 통해 3년/5년 등 법정 보관 주기 경과 리드는 영구 파기 상태로 전환.
